Vue d'ensemble

Synégo est un monorepo : une API ASP.NET Core, un front React servi par nginx, et l'infrastructure (Docker Compose, scripts serveur, CI) versionnée au même endroit. Tout tourne en conteneurs, en développement comme en production.

Parcours d'une requête

  1. Le navigateur charge le front depuis nginx (HTTPS). Il se connecte directement à Firebase Auth, qui lui remet un jeton d'identité.
  2. Chaque appel /api/… porte ce jeton (Authorization: Bearer). nginx limite le débit puis relaie vers l'API.
  3. L'API vérifie la signature du jeton auprès de Google (securetoken.google.com/<projet>), retrouve ou crée le compte en base, et lit le rôle en base (jamais dans le jeton).
  4. Les rendez-vous sont pris dans l'iframe Calendly ; le front confirme la réservation à l'API, qui la relit chez Calendly (et le webhook la synchronise sur une offre payante).

Docker contourne UFW

Un port publié par Docker est ouvert même si UFW le refuse. Règle du projet : ne publier que 80, 443 (et 8443 pour Zabbix) sur toutes les interfaces ; tout autre port est lié à ${ADMIN_BIND_IP} dans compose.yaml.

TLS et en-têtes

  • Certificat Let's Encrypt obtenu par install.sh (webroot), renouvelé par le conteneur certbot ; nginx recharge les certificats toutes les 12 h (synego-reload-certs). Sans certificat, un auto-signé temporaire permet de démarrer.
  • EXTRA_DOMAINS ajoute d'autres noms au même certificat (production : synego.duckdns.org).
  • En-têtes : CSP stricte (sources : soi-même, Google pour l'authentification et reCAPTCHA, Calendly), HSTS, X-Frame-Options, nosniff. font-src 'self' : aucune police en data: (Vite configuré pour ne jamais les intégrer).
  • Limite de débit : 10 req/s par IP sur /api (rafale 40) côté nginx ; 10 envois par 10 minutes et par IP sur les formulaires publics côté API.

Authentification et rôles

  • JwtBearer valide l'émetteur, l'audience (Firebase__ProjectId) et la signature des jetons Firebase.
  • Un IClaimsTransformation (UserProvisioning) crée le compte applicatif à la première requête et ajoute le rôle lu en base : Prospect, Client (signé) ou Coach.
  • Les e-mails de Admin__Emails deviennent Coach uniquement si l'adresse est vérifiée par Firebase. Un coach peut en nommer d'autres (invitations) mais pas se retirer lui-même.
  • Back-office : politique « Coach ». Option ADMIN_VPN_ONLY=true : l'API exige en plus l'en-tête X-Synego-Zone: admin, posé uniquement par le bloc nginx de la zone admin (le bloc public l'écrase).

Fichiers et données

  • Dépôt de documents : PDF, PNG, JPEG, DOCX, XLSX, PPTX ; 10 Mo maximum ; extension et signature binaire vérifiées ; nom de stockage aléatoire ; téléchargement uniquement par l'API après contrôle du propriétaire.
  • Suppression d'un document : douce (DeletedAt), purge définitive après 30 jours. Un client ne supprime que ses propres dépôts.
  • Calendly : l'API ne suit que des URI api.calendly.com (pas de SSRF) ; webhook signé HMAC, accepté pendant 3 minutes.

Services de fond

  • Rappels (ReminderService) : toutes les 5 minutes (IntervalMinutes), envoie le rappel 48 h (bouton d'annulation) aux rendez-vous entre 24 et 48 h, puis le rappel 24 h (lien Meet, plus d'annulation). Un rendez-vous pris tard ne reçoit que les rappels encore utiles. Les envois sont marqués en base (Reminder48SentAt, Reminder24SentAt) : jamais de doublon.
  • Purge des documents (DocumentService) : efface définitivement les fichiers supprimés depuis plus de 30 jours.

Intégration Calendly

  • La coach colle un jeton personnel dans le back-office ; l'API le vérifie, le chiffre, puis liste ses types d'événements.
  • Chaque type du site (Booking:Types) est associé à un événement Calendly, masquable ; webhook automatique sur offre payante.
  • Réservation : l'iframe envoie calendly.event_scheduled ; le front appelle /api/booking/confirm, l'API relit l'invité chez Calendly (idempotent sur l'URI) et récupère le lien de visio (location.join_url).

Points d'implémentation

  • Routes : site public, /connexion, /inscription, /espace/* (connecté), /admin/* (Coach). Les pages sont chargées à la demande (lazy) ; le back-office interroge /api/admin/overview toutes les 60 s pour ses pastilles.
  • Langues : dictionnaire typé, langue mémorisée (synego:locale) ; ajouter une langue = copier en.ts et la déclarer.
  • Thème : suit le système, mémorisé (synego:theme) ; couleurs en variables CSS dans index.css.
  • Mouvement : MotionConfig reducedMotion="user" ; Lenis désactivé si l'utilisateur réduit les animations.
  • Polices auto-hébergées (Fraunces, Hanken Grotesk) : aucune requête vers Google Fonts.
  • Dialogues à la marque (confirm, ask, toast) à la place des fenêtres natives du navigateur.

Configuration Firebase côté navigateur

src/auth/firebase.ts lit VITE_FIREBASE_* depuis le .env (lu par Vite en développement, passé en build args à l'image nginx en production). La clé web n'a aucune valeur de repli dans le code : si elle manque, le site s'affiche et la connexion échoue avec un message clair (auth/invalid-api-key). Les autres identifiants (projet, domaine d'authentification, identifiant d'application) gardent un défaut public.

VITE_FIREBASE_PHONE_TEST_MODE=true désactive la vérification d'application pour les numéros de test déclarés dans la console Firebase.

Déploiement par pull (deploy/vps/synego-deploy.sh)

  1. synego-deploy.timer lance le service toutes les 2 minutes (et 2 minutes après le démarrage du serveur). Un verrou empêche deux déploiements simultanés.
  2. git fetch : si origin/main n'a pas bougé, rien à faire.
  3. État de la CI du commit lu par l'API publique de GitHub (check-runs) : en cours → on attend ; échec → on ne déploie pas.
  4. Sauvegarde de la base (backup.sh), puis git checkout du commit et docker compose up -d --build --remove-orphans.
  5. Contrôle de https://localhost/api/health : succès → commit écrit dans .deployed, anciennes images nettoyées ; échec → retour au commit précédent et reconstruction.
journalctl -u synego-deploy -f                      # suivre les déploiements
systemctl list-timers synego-deploy.timer           # prochain passage
/opt/synego/deploy/vps/synego-deploy.sh --force     # déployer sans attendre la CI (urgence)

Option : GITHUB_TOKEN dans /etc/synego-deploy.env si le dépôt devient privé.

Installer un serveur

Un serveur Ubuntu ou Debian neuf, en root, une commande. Le script est rejouable sans risque.

curl -fsSL https://raw.githubusercontent.com/luidgi-gaudin/projetkine/main/deploy/vps/install.sh \
  | ADMIN_EMAILS=coach@exemple.fr FIREBASE_API_KEY=<clé web> bash

Ce que fait install.sh

  1. Paquets, Docker et Compose v2, swap de 2 Go si moins de 3 Go de RAM ; pare-feu UFW (22, 80, 443, 51820/udp).
  2. Clone de main dans /opt/synego. Un dossier existant sans git est mis de côté (rien n'est supprimé) ; un .env étranger est renommé et remplacé.
  3. .env : mots de passe aléatoires, DOMAIN (défaut <ip>.sslip.io), ADMIN_BIND_IP=127.0.0.1, projet Firebase, coach, clé web.
  4. Zabbix détecté : ADMIN_PORT=8444 et génération de compose.override.yaml.
  5. Ports 80/443 libérés si un autre conteneur ou service les occupe (arrêté, pas supprimé), puis construction et démarrage.
  6. Certificat Let's Encrypt pour DOMAIN et EXTRA_DOMAINS, rechargement de nginx.
  7. Installation et activation de synego-deploy.service et synego-deploy.timer.

Sauvegardes et test de restauration

Chaque nuit à 2 h et avant chaque déploiement : pg_dump du schéma synego au format custom, chiffré AES-256 (BACKUP_PASSPHRASE), rotation à 14 jours, dans /opt/synego/backups. À ajouter : une copie hors du VPS.

Tester sans toucher à la production : restaurer dans une base temporaire.

docker compose exec -T db psql -U postgres -c "create database synego_restore_test owner synego_owner"
docker compose exec -T db psql -U postgres -d synego_restore_test -c "create schema synego authorization synego_owner"
docker compose exec -T backup sh -c 'f=$(ls -1t /backups/synego_*.dump.enc | head -n1);
  openssl enc -d -aes-256-cbc -pbkdf2 -pass env:BACKUP_PASSPHRASE -in "$f" -out /tmp/t.dump &&
  PGUSER=synego_owner PGPASSWORD="$SYNEGO_OWNER_PASSWORD" pg_restore --no-owner --schema=synego -d synego_restore_test /tmp/t.dump'
# comparer les comptages avec la base réelle, puis :
docker compose exec -T db psql -U postgres -c "drop database synego_restore_test"

Test réalisé le 4 novembre 2026 : restauration, effacement volontaire d'un compte dans la copie, nouvelle restauration, compte retrouvé.

Changer la clé web Firebase
